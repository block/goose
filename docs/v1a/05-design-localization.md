# 设计与本地化约束

## V1 视觉原则

新主线仓库不再追求当前 `CSO` 那种 Accio-parity 的重定制壳层。

V1 应采用：

- Goose Desktop 原生壳
- 替换品牌名、图标、产品文案
- 对中国安全人员更友好的默认语言与能力入口

也就是说：

- **复用 Goose 的交互骨架**
- **做安全产品化的轻定制**

不要在 V1 为了视觉“像另一个产品”，重写大面积 UI。

## 用户心智

中国安全工作人员对产品的理解通常不是：

- provider
- extension
- recipe
- persistent instruction

而是：

- 研判
- 分析
- 调查
- 验证
- 报告
- 工具

所以 UI 要把底层 Goose 能力翻译成“任务语言”。

## 默认语言策略

- 默认语言：`zh-CN`
- 辅助语言：`en-US`
- 语言切换：设置中可改

V1 必须完成中文化的内容：

- 应用名
- onboarding
- 模型标签与模型说明
- 默认 skill/recipe 名称
- 设置页关键项
- 常见错误文案
- 任务入口文案

V1 可以后置的内容：

- 深层开发者诊断页的全部中英切换
- 少量边缘系统消息的完整双语覆盖

## 信息架构翻译

建议映射如下：

| Goose 概念 | 用户可见中文 |
| --- | --- |
| Session | 会话 |
| Skill | 技能 |
| Plugin | 插件 |
| Extension / MCP | 扩展 / 工具连接 |
| Recipe | 任务模板 |
| Memory | 记忆 |
| Provider | 模型通道 |
| Model | 模型 |

在主路径里，进一步翻译为任务语义：

| 产品入口 | 底层能力 |
| --- | --- |
| 漏洞研判 | skill + recipe |
| 告警分析 | skill + recipe |
| 网页调查 | MCP + browser |
| 报告生成 | skill + template |

## 模型切换命名

你的目标用户是安全工程师，因此第一层模型选择应展示：

- `Auto`
- 后台已开放的真实模型名

例如：

- `DeepSeek V4 Flash`
- `DeepSeek V4 Pro`
- `Kimi K2.6`
- `GLM 5.1`

不要把主入口硬翻成：

- `快速`
- `深度`
- `研判`

这种抽象模式。

可以做的中文化是：

- 给模型补充中文说明
- 给模型加标签，如 `推荐`、`付费`
- 给模型补充能力描述，如 `低延迟`、`长上下文`、`强推理`

高级页再展示：

- 本地模型
- 自定义 OpenAI-compatible
- 自带 API key

## 首页与首屏

首页的默认任务建议直接服务安全人员：

- 研判一个漏洞
- 分析一条告警
- 调查一个 IOC
- 抓取一个安全网页情报
- 生成一份安全报告

避免首屏像通用聊天产品那样过于泛化。

## 默认角色

V1 建议内置一个默认角色：

- `安全分析助手`

可扩展角色：

- `漏洞研判助手`
- `告警调查助手`
- `威胁情报助手`
- `报告生成助手`

这些角色优先通过：

- system prompt
- recipe
- skills

组合出来，而不是写一套新的 agent persona framework。

## 语气与术语

默认语气：

- 直接
- 审慎
- 结果导向
- 明确不确定项

输出习惯更接近安全报告，而不是营销文案：

- 结论
- 证据
- 风险
- 不确定性
- 建议下一步

## 中英文本组织

建议目录：

```text
distro/security-cn/locales/
├── zh-CN.json
└── en-US.json
```

建议拆分命名空间：

- `shell.*`
- `settings.*`
- `models.*`
- `tasks.*`
- `skills.*`
- `errors.*`

## 品牌替换范围

V1 需要替换：

- App name
- Logo / icon / splash
- 默认 system prompt 中的助手名
- 打包产物名
- 更新源与发布名

V1 不要求：

- 整个 UI 视觉语言完全脱离 Goose

## 设计验收标准

- 用户打开就知道这是安全工作台，不是通用聊天工具
- 默认语言和入口符合中国安全人员习惯
- 第一层入口是任务，不是技术名词
- 品牌替换完整
- 不为了视觉重写整套 Goose UI
