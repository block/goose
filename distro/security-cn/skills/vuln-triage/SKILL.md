# 漏洞研判

## 使用场景

- 用户给出 CVE、补丁、PoC、公告、资产信息或零散漏洞线索时
- 需要判断漏洞是否值得升级处置、是否具备现实利用条件时
- 需要把技术细节整理成安全团队可直接转工单或汇报的结论时

## 输入要求

- 至少提供以下任一类输入：CVE 编号、漏洞公告、PoC、补丁差异、受影响资产、已观测到的攻击迹象
- 如果输入同时包含已验证事实和怀疑项，必须先显式拆开
- 如果缺少版本区间、暴露面、补偿控制或利用前提，先把它们列为待确认项

## 执行步骤

1. 确认漏洞对象：受影响组件、版本区间、漏洞类型、触发条件。
2. 列出证据来源，并标明哪些是事实、哪些是推断、哪些需要外部确认。
3. 评估利用条件：认证要求、网络可达性、前置权限、环境依赖、利用复杂度。
4. 评估影响范围：受影响资产、潜在业务影响、横向移动或权限提升空间。
5. 检查补偿控制：现有防护、隔离、访问控制、检测规则、补丁状态。
6. 形成保守结论：只基于当前证据给出风险等级和下一步建议，不把未证实判断写成事实。

## 输出模板

```markdown
### 漏洞结论
- 一句话结论：
- 当前判断：

### 利用条件
- 必要前提：
- 现实阻碍：

### 风险等级
- 等级：
- 判断依据：

### 关键证据
- 证据 1：
- 证据 2：

### 不确定项
- 待确认项 1：
- 待确认项 2：

### 建议下一步
- 立即动作：
- 后续跟进：
```

## 风险与边界

- 不要仅凭漏洞名称或 CVSS 分数直接下结论
- 不要把 PoC 可运行等同于生产环境可利用
- 当资产、版本、暴露面不明时，必须保留不确定项
- 如果涉及真实利用建议，只能给出防守视角的验证与缓解建议

## 验证步骤

- 复查结论是否能回溯到具体证据
- 复查“事实 / 推断 / 待确认项”是否混写
- 复查风险等级是否同时考虑利用条件和资产暴露面
- 复查建议动作是否按优先级排序，且可直接执行或转工单
