# IOC 研判

## 使用场景

- 用户给出域名、IP、URL、Hash、邮箱、证书、样本线索时
- 需要把零散 IOC 做富化、归并、去重和可信度判断时
- 需要输出可直接进入威胁情报或事件调查流程的结构化摘要时

## 输入要求

- 明确 IOC 类型，并尽量保持一条输入只承载一种主要对象
- 如果输入来自告警、样本、邮件或网页，说明来源和时间点
- 如果有多个 IOC，先去重并按类型分组

## 执行步骤

1. 识别 IOC 类型，并标准化格式。
2. 按来源拆分事实与推断，记录采集时间和上下文。
3. 检查关联关系：解析跳转、域名与 IP 绑定、样本与下载链路、账号与基础设施复用。
4. 判断可信度：单点命中、跨源一致性、时间有效性、噪音特征、误报可能性。
5. 提取下一步建议：继续富化、封禁、监测、下沉到告警或事件调查。

## 输出模板

```markdown
### IOC 摘要
- 类型：
- 值：
- 来源：

### 关键发现
- 发现 1：
- 发现 2：

### 关联关系
- 关联 IOC：
- 关联方式：

### 可信度判断
- 结论：
- 依据：

### 建议下一步
- 继续富化：
- 防守动作：

### 待确认项
- 待确认项 1：
- 待确认项 2：
```

## 风险与边界

- 不要把单一情报命中直接写成恶意定性
- 不要忽略 IOC 的时间效应和上下文差异
- 如果同一 IOC 同时存在恶意和正常使用场景，必须写清边界
- 不能验证的关联关系只能写成“疑似”或“待确认”

## 验证步骤

- 复查 IOC 类型和格式是否标准化
- 复查结论是否清楚区分事实、关联和推断
- 复查可信度判断是否说明依据和反例
- 复查建议动作是否与可信度等级一致
